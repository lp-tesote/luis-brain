# 2026-05-14 — UI redesign foundation + Saldos page design + impl specs

## Full session — building the design spine, then the first page on top of it

Big foundation day. Started with "let's work on the UI re-design of Tesote" — no specific page yet — and ended with a fully-spec'd Saldos page promoted to the team KB. The pattern: build the system layer first (archetypes + density + tokens), then validate it by designing one real page beginning-to-end, then write the impl specs both audiences need.

The whole arc moved through three altitudes: **tokens → primitives-via-archetypes → page**. We never wrote a `primitives.md` doc — primitives extracted themselves from the prototype as we built it, which validated the "build the visual prototype first, derive primitives from it" approach. Markdown-first design systems rot; this didn't.

### Design system foundation

Confirmed the 5 → 6 screen archetypes with Luis: **list/table · detail/record · form/flow-step · dashboard · empty state · onboarding**. Each got ASCII wireframes + anatomy + Tesote examples + variants in [[../product/design/archetypes]].

**Density reframed mid-session.** Original spec called 44px "standard for all list pages." Luis caught the right insight by comparing Mercury's spacious Payments inbox to Mercury's dense Transactions ledger: **density is task-driven, not archetype-driven.** Reframed to 3 buckets in archetypes.md:

- **36px** — browse / scan (Transacciones, GL, conciliación)
- **44px** — manage a set (Contrapartes, Saldos, Bancos)
- **52px** — review and decide (Pagos, Cobros, Disputas, Approvals)

Mapped every known Tesote screen to one of the three. Future Transacciones will be tight; Pagos went roomier on the v2 prototype.

**Typography locked** in [[../product/design/design]]: full migration to Inter Tight (display) + Aspekta (body, with Inter fallback until Aspekta is self-hosted). No more in-product Inter-only exception. Font scale snapped to `11 / 12 / 13 / 14 / 16 / 18 / 22 / 28`. Page titles = 26px.

**Pill dots restored** with semantic colors after Luis pushed back on the "pills feel unexciting" reaction. Lunour ramp-600 dots: blue / yellow / orange / green / gray-500. Pastel background stays calm; tiny colored dot restores scannability. This is the Mercury / Linear pattern.

### Saldos page — full design + 3 prototypes

This is the operational trust dashboard for Tesote. If users don't trust the saldos here, they can't trust anything downstream. Stakes are high; design needed to clarify, not invent.

**Naming locked:** Saldos (not Cuentas or "Panel de Sincronización"). Job over object. CFO/treasurer-flavored. Lives under Tesote Connect.

**Load-bearing clarification from Luis:** **data certification is for transacciones, not saldos.** Saldos are 99% reliable as pulled from banks. The current UI's "Validación" column on Saldos is misplaced — it belongs on the Transacciones page, where transaction completeness is a real concern. This collapses per-row trust signals on Saldos from 3 → 2, then to 1 composite badge. Captured in [[../product/connect/saldos/design]] as a "Critical clarification" section.

**Estado model evolved fast** (good iteration):

- v1: 5-state composite (Al día / Sincronizando / Atrasado / Rota / Manual)
- v2: same 5 after the certification clarification
- **v3 final (locked):** 3 states only — 🟢 **Sincronizada** · 🔵 **Sincronizando** · 🟡 **Requiere atención** + manual = `—`. Recency lives in a separate "Último sync" column as data, not status. Luis: "I'd 100% keep the último sync info." Right call — simpler model, less cognitive load.

**Conexiones gets richer vocabulary** because it's the diagnostic page:
🟢 Activa · 🔵 Sincronizando · 🟡 Cambio credenciales · 🟡 Requiere 2FA · 🔴 Banco caído · ⚪️ En revisión · 🟡 Sync falló · Manual. Different scope, different vocabulary, same visual treatment so the badge family feels coherent.

**Sync philosophy locked (Option A):** Saldos is read-only — small inline `↻ refrescar` link only. All sync actions live on Conexiones. **No sync-all button anywhere** — per Luis: "we need individual syncs, this is a system decision because it would overload our systems." Per-connection sync buttons on Conexiones rows. Per-account sync killed everywhere (API doesn't support it).

**Three prototypes shipped:**

- [[../product/connect/saldos/prototypes/saldos-v1]] — grouped table exploration (preserved for v2 revisit when volume warrants)
- [[../product/connect/saldos/prototypes/saldos-v2]] — flat list + Conexiones view added, JS toggle works
- [[../product/connect/saldos/prototypes/saldos-v3]] — **canonical** — currency prefix in Saldo column, 3-state Estado, 2FA tag, per-row Conexiones sync, multi-select filter dropdowns + search that recalculate currency totals live, "filtrado" badges on cards, richer Conexiones statuses, overflow ⋯ killed everywhere

The filter + currency recalculation interaction is the polish that makes the page feel alive. JS works end-to-end.

### Implementation specs — two audiences, two artifacts

Luis's framing: "it's going to be written by our ai agent, with all the context it has." So we built **two specs**, deliberately non-overlapping in detail:

- [[../product/connect/saldos/spec-eng]] — strategic brief for a human eng reviewer (Dan). Covers: why, scope, decisions already locked, user context (10×30+ scale, multi-currency default, per-connection-sync constraint), risks + tradeoffs, open questions, suggested phasing. Points at spec-agent.md for detail.
- [[../product/connect/saldos/spec-agent]] — granular imperative spec for an AI coding agent. Opens with a literal `READ FIRST` block (file paths the agent loads before generating code). TypeScript data contracts. State machines as transition tables. 11 testable acceptance criteria with exact values. Out-of-scope list. Performance budgets. Telemetry events with payload shapes. Prototype DOM-hook reference table so the agent can grep the HTML.

**Scope boundary made explicit and unmissable** after Luis confirmed: "we only want to touch what's inside the saldos page. we don't want to touch the side bar, or the nav bar." Both specs now have a hard `SCOPE BOUNDARY` section listing what's IN scope (page + page-internal components) and what's OUT (sidebar, topbar, app shell, global nav, other routes) with ❌ markers + a "stop and ask" instruction for the agent if it finds itself editing outside the page directory. AI agents over-build when scope is fuzzy.

This pair is the new pattern: **human brief + agent spec, side-by-side, non-overlapping**. The prototype HTML is the visual contract; the agent spec is the behavior contract.

### Key decisions locked today

1. **Six archetypes** for Tesote product UI (list/detail/form/dashboard/empty/onboarding)
2. **Density is task-driven, not archetype-driven** — 3 buckets mapped to every Tesote screen
3. **Full Inter Tight + Aspekta migration** for product UI (no Inter-only exception)
4. **Font scale** `11 / 12 / 13 / 14 / 16 / 18 / 22 / 28`
5. **Workspace-shell284.html** is the design canonical (different from engineering canonical `workspace-shell.html`)
6. **Saldos** as the name (job over object)
7. **Data certification is for transacciones, not saldos** — load-bearing, ripples through whole page design
8. **3-state Estado on Cuentas** (Sincronizada / Sincronizando / Requiere atención) + manual = `—`
9. **Richer Estado vocabulary on Conexiones** (8 states, including red `Banco caído` and gray `En revisión`)
10. **Sync philosophy:** Saldos is read-only with inline refresh hint; all sync actions on Conexiones; **no sync-all button anywhere**; per-connection only
11. **Scope boundary:** implementation touches Saldos page content area only; never modifies sidebar/topbar/app shell

### What worked, what to remember

- **"Build the visual prototype first, then derive primitives from it"** was the right call. Specs without visuals are unfalsifiable. Luis has great taste and is a see-and-correct designer — the path through ASCII wireframes → archetypes doc → real HTML → iterate worked because each step gave him something concrete to react to.
- **Versioned prototype siblings** (v1 grouped, v2 flat, v3 final) preserved the exploration without losing intermediate state. Per [[feedback_versioning_progression]].
- **Two-spec model for eng handoff** (human brief + agent spec) is the new pattern. Worth memorializing as a project convention.
- **Iterative design conversation works** when the agent surfaces decisions as they emerge (3-state vs 5-state Estado, density-by-task, sync philosophy options A/B/C) rather than implementing in one shot.
