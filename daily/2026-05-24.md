## Late session — Tesote AI use-case taxonomy + v0.1 mockup

Stepped back from "more gallery cards" and rebuilt the AI capability map from scratch. The current taxonomy is **tool-centric** (Working in Odoo / Files / Rules / FX / Analysis — groups by what Claude can do), which hides the more important axis: *what is the user actually trying to accomplish, and how should it execute*. Result: a new internal taxonomy doc + a v0.1 HTML mockup of how it would render in the `/ai` surface.

### The frame that locked in

Two axes, both load-bearing:

1. **Job-to-be-done** (not "department"). VE finance teams are 1–3 people wearing all hats, so "AP clerk vs AR clerk" is artificial. Real jobs: *close, pay, collect, reconcile, run cash/FX, forecast, comply with SENIAT, comply with banks/BCV, maintain master data, report up, investigate, payroll touchpoints*. 12 total. Aligns with [[project_tesote_ai_audience]] — frame copy as "finanzas," not "tesorería."
2. **Execution mode** — *autopilot / draft-approve / scheduled / on-demand chat*. This is the axis the current gallery hides entirely. Most "AI use cases" should not be chat prompts at all; they should be rules + drafts + crons that the chat only *configures* and *audits*.

### The architectural rule the taxonomy forces

> If a workflow can be specified deterministically, it does not belong in chat.

Chat is for (a) ad-hoc analytical questions, (b) configuring/inspecting Automations rules, (c) genuinely judgment-driven work. Everything else routes to a separate `/automations` surface **that doesn't exist yet but the taxonomy demands.**

Concretely: ~70% of what's in the current AI gallery — BCV lookup, "categoriza CANTV," "postea la factura," "crea regla NOMINA → Sueldos" — is Automations work that's been awkwardly stuffed into chat because Automations isn't built. **The gating roadmap unlock isn't more chat prompts; it's the Automations surface.**

### The meta-pattern I didn't see in my own v0.1

After Luis added (a) cash-flow-by-category reports, (b) gastos deducibles / SENIAT receipt-chase for card spend, (c) comprobantes de retención chasing (when client is contribuyente especial), a cross-cutting pattern surfaced:

**Documentary evidence management.** § 7.a (gastos deducibles), § 7.b (comprobantes recibidos), § 3.a (comprobantes a recibir) are *the same machine* applied to three document types — per-txn "documents expected" model, ingestion pipeline + OCR, validation rules per type, "documents at risk" surface pre-close. **One unified build, not three separate features.** Probably the cleanest first `/tesote-plan` target out of the entire taxonomy because the customer ROI is concrete:

> Customer spends $50k/year on cards. Today they lose ~37% of it (~$18.5k) in tax credits they're already entitled to but can't claim because the receipt is missing or wrong. Tesote sees the txn the moment it hits the bank feed and chases the receipt automatically. The math sells itself.

Same shape as the Banesco "botón de pago = cobros" insight from earlier this month: high-stakes, well-bounded, mechanical workflow that's pure pain for the finance team and pure execution for Tesote.

### Three substrates the taxonomy named

1. **Documentary evidence management** (above) — highest leverage.
2. **Categorization as substrate** — §§ 1, 4, 5, 6, 10 all depend on txns being categorized correctly. The rules system is the floor; everything else is reporting on top.
3. **Reconciliation as substrate** — §§ 1, 2, 3, 4, 5, 7, 12 all assume bank movements have been matched to Odoo. Not really a "job" — invisible plumbing that, when working, makes every other report trustworthy.

Worth treating these three as the **build order** for Automations, not as separate features.

## Late evening — Winning vs. horizontal AI (Harvey/Legora playbook)

Mobile session. Started from two parallel questions: (1) how does Tesote AI win when Claude/ChatGPT + a generic Odoo MCP become a real stack in LATAM, and (2) what are Harvey and Legora doing in legal-AI that we should be copying rather than re-inventing.

The two questions collapse into one frame: **Harvey and Legora don't beat ChatGPT on model quality — they beat it on the wiring around the model.** Same play applies to Tesote AI. The moat isn't the LLM; it's the verticalized substrate (data + workflows + citations + audit + multi-player + domain language).

### Five structural reasons we win vs. a generic Odoo MCP

1. **Odoo is one system; finance is N.** A perfect Odoo MCP only sees Odoo. It doesn't see BNC, Banesco, Provincial, WhatsApp threads, payment links, multi-jurisdiction state. Tesote is the only layer that joins them (the command-center thesis).
2. **MCP exposes data; Tesote executes work.** Querying is easy. Sending a Banesco link, debiting via BNC, running multi-touch cobranza with memory — that's the action layer we own.
3. **Generic chat ≠ product.** A controller wants a button ("show me what to chase this week"), not a prompt. We pre-bake the joins, prompts, workflows, bank dialects.
4. **LATAM/VE ontology isn't in Odoo's schema.** BCV vs paralelo, RIF, comprobantes, multi-jurisdiction, bank aliases ([[../reference_ve_bank_naming]]) — our data, not Odoo's.
5. **Audit, multi-tenant, role-gated action.** Generic agents can't transact safely. We can.

> If Odoo MCP is git for accounting, Tesote AI is the IDE.

### How Harvey/Legora maps onto the existing frame

Critically: this **doesn't reorganize** the work in [[../product/ai/use-case-taxonomy|the use-case taxonomy]] — it *ratifies* it and adds UX vocabulary + market evidence.

| Their move | Our existing frame | Net effect |
|---|---|---|
| Workflows not chat | Architectural rule already locked (deterministic → Automations) | Validates + adds urgency to actually build Automations |
| Legora's "do N things" table | Automations drafts queue | Concrete UX precedent — copy it |
| Harvey citations on every output | Documentary-evidence pattern (§§ 3.a, 7.a, 7.b) | Citations and doc-evidence are the *same primitive* |
| Speak like the user | "Finanzas" not "tesorería" + VE-tú | Already locked |
| Multi-player by default | Command-center architecture | Already locked |
| Land-and-expand via reference accounts | Mariel + pick 2–3 more | Pilot list IS the candidate pool |
| Narrow + deep beats broad + shallow | "Pick 1–2 jobs to deepen" next-move | Doc-evidence triplet is the first flagship |

### What this actually changes

**One real change to existing plans:** the rollout-video draft is 3 chat demos. Harvey/Legora would say at least one should be an **Automations "while you slept" delegation moment** — show the user *delegating*, not just querying. Proposed swap:

> *"And while you slept, Tesote chased 14 receipts, marked 12 as deducible-eligible, and recovered $2,340 in tax credit you would have lost. Here's the pre-approval queue."*

Speed is a feature. Delegation is the product. The Q I left open with myself this morning ("should the rollout video mention the Automations layer") just got answered — yes, at least one demo moment.

**The other thing that hardens:** the Automations surface IA isn't v2, it's the gating roadmap unlock. First `/tesote-plan` priority should be Automations IA + doc-evidence ingestion pipeline, not another chat feature.
